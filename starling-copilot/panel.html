      🧠 Style Brain 
      
Feed official style-guide docs (Lark, PDFs, pages). The copilot distills each into compact rules + glossary terms, merges them into one curated brain, and applies it in 🐦 Starling and ⚖️ Feishu LQA — on top of the built-in guide. Its content is sent to OpenAI (distillation + each suggestion), like your translations.

      
      

        
        
        
        
      

      

      

      

        📚 Learn from a Starling task — harvest approved translations
        
Open a submitted task in Starling, then Harvest — it reads every proofread-confirmed (approved) segment. Works on both the String editor and the Document editor (for doc tasks it reads the open editor's data directly, so keep that tab open). Two independent actions on the result: ➕ Add pairs to memory drops them into Consistency memory (exact source→target, no GPT); 🧠 Distill turns them into new Style-Brain rules/terms. Either way, anything that conflicts with an existing entry — a source already remembered with a different target, or a rule/term that clashes with the brain — is parked in the orange ⚠ Conflicts card for you to adjudicate; nothing overwrites without your pick.

        

          
          
        

        

        

          
          
        

      

      

        🧹 Consolidate rules — merge duplicates & tighten
        
One GPT pass over your existing rules, per category: merges rules that say the same thing, drops near-duplicates, and tightens wording — without losing coverage. Why it matters: a brain applied as a 1,000+-line wall gets skimmed by GPT (attention dilution) and costs a fortune to send on every batch; a tight ruleset is actually followed. Glossary, locked terms, memory and auto-fix are left untouched. A full backup downloads first; you review the result and click Replace — nothing changes until then, and the backup makes it reversible.

      🧠 Consistency memory 
      
Every segment you write is remembered (source → your target). When the same source turns up again, your previous wording is filled in so it stays identical. If GPT proposes something different, the card is left unchecked (🧠 memory — review) so you confirm it — a remembered mistake never re-applies silently, and writing a corrected version overwrites the memory.

Store a source → your target directly (same as if you'd written it). Next time that exact source appears, this wording fills in. Overwrites any existing entry for the same source.

      🔒 Locked terms 
      
A mandatory glossary. Each EN→HE pair here is sent to GPT as non-negotiable (it may only add a Hebrew prefix), and after every Run any segment whose source contains the term but whose target is missing the required Hebrew gets a red 🔒 locked term flag so it can't ship. It never auto-edits your text — so it can't break Hebrew grammar; you fix flagged rows by hand and the flag clears. Applies in 🐦 Starling and ⚖️ Feishu LQA.

      🩹 Auto-fix 
      
A deterministic scanner that runs after GPT and rewrites the target to your locked corrections — e.g. a plural imperative GPT still returned becomes your singular gender-slash: שלמו→שלם/י, הצטרפו→הצטרף/י. Whole-word (a leading ו is kept), applied to both 🐦 Starling and ⚖️ Feishu outputs. Each change is badged ✎ auto-fixed in Review and reverts if you edit the row. It's a dictionary you lock in (both sides), so irregular verbs stay correct (נסו→נסה/י, not נס/י).

      🏷 Term base 
      
Reads Starling's own inline term references — the dotted-underline words in the Source column whose hover shows an approved EN→HE, a part-of-speech, and a DNT (do-not-translate) / Brand flag. Open a task and click ⬇ Grab term base — it reads every term in the task, then splits them into two tiers. (In the String editor it scrolls the whole virtualized list; in the Document editor it reads them straight from the task data.) DNT / brand terms (e.g. TikTok) go into 🔒 Locked terms as keep-as-is (strict). Translatable terms (e.g. content → תוכן) are kept here as soft hints: injected per-segment into the GPT prompt as the preferred rendering that may bend when grammar/context requires (a Noun used as a verb, "due to" → עקב), and surfaced as a 🏷 term review flag on deviation — never forced.

      🔤 Phrase mining 
      
Mines the built 📦 Corpus for recurring EN→HE terms (sub-segment, not whole strings) — so it catches drift buried across different sentences (e.g. guardian → אפוטרופוס / הורה). Consistent terms → add to the Style-Brain glossary; drift terms → pick a canonical (+ optional Auto-fix). Deterministic, no GPT, no cost. Build the corpus first. After mining you can optionally ✨ Refine with GPT — it reconstructs a clean canonical term from your real examples (e.g. LIVE on TikTok → שידור חי ב-TikTok, not בשידור) and drops non-terms.

      
      

      

    


    

      📚 Learn from whole corpus 
      
One GPT pass over every pair in the built 📦 Corpus — extrapolates rules, terms, expressions & exceptions, then reconciles them against your current brain and flags anything that conflicts. Pairs are read newest-submitted first (later work is more reviewed), and for a source you rendered several ways over time it sees the evolution timeline so it learns the correction, not both. Findings land in the same 🧠 Style Brain review list (New rules / terms / ⚠ conflicts) — tick what to merge, or Discard to keep the brain as-is. A full backup of every brain downloads automatically before you can merge. Uses your chosen model; a ~9k-pair corpus is a few dollars, one-off. Build the corpus first.

      
      

      

    


    

      ⚠ Conflicts to resolve 
      
A glossary term or a remembered source can hold only one target. When a new pairing clashes with a stored one, it's parked here instead of silently overwriting. Each value is ✎ editable — fix the wording if neither side is quite right, then click the side you want (it saves exactly what's shown); the other is deleted.

      ℹ️ How assisted (tagged) segments work
      

        
Some segments contain real inline tags — the yellow ①② markers in Starling. Typing over the whole cell would destroy those tag objects, so the extension never auto-writes them. They're marked ✋ paste by hand in the review.

        
It still proofreads / translates them for you, and when a segment is a bullet list (A • B • C — each item wrapped in its own ①…① pair) it splits the corrected text into numbered parts.

        
To apply one:

        
    
          
  1. Click Copy on a part (its badge number matches the tag number in Starling).
    2. 
          
  2. In the Starling cell, select only the text between that part's ①…① tags.
    3. 
          
  3. Paste. The tag objects stay exactly where they were — you only replaced the text.
    4. 
        

        
Everything without tags is still written automatically in step 4. This keeps the fragile tag surgery in your hands (reliable) while the extension does all the mechanical work around it.

        ℹ️ How Feishu LQA works
        

          
The task owners ran a global AI translation check and listed suspected errors in a Feishu sheet. For each row you decide whether the AI-flagged error is valid (real → fix it in Starling) or invalid (false positive).

          
Feishu sheets are drawn on a <canvas> — the cells aren't real HTML, so this can't scrape them. Instead you paste the rows (Ctrl+C copies them as tab-separated text), or load an .xlsx / CSV / TSV — for an .xlsx, pick the sheet tab (e.g. 8.5 sync) — and it runs gpt-5.4 per row. The sync tabs stack he/jv/ko together, so the Language selector defaults to Hebrew only and hides the other locales.

          
It fills the sheet's 5 Linguists columns:

          
    
            
  1. Valid (Yes/No) — is the AI error real.
    2. 
            
  2. Category — one of the sheet's 9 error types, only when Valid = Yes.
    3. 
            
  3. Final Translation — the corrected Hebrew, only for valid issues.
    4. 
            
  4. Updated on Starling — left blank; you tick this as you apply each fix.
    5. 
            
  5. Comments — the invalid reason, only for invalid spelling/grammar errors, one per type (deduped, per the task email).
    6. 
          

          
Runs locally with your OpenAI key. Only the text columns go to GPT — the Feishu doc never leaves this browser. Keep shared-account credentials out.

        ℹ️ How Sheet → Starling works
        

          
This drives the manual write-back: for each valid fix it filters Starling's All tasks by Key (en→he), you open the task, and it reads the live segment, writes the Final Translation, and proofread-confirms that one row.

          
It never blind-pastes. A key can live in several tasks, a task's source can differ from the sheet's, and a task comment can overrule the sheet — so it always shows you live source vs. sheet source and current target vs. final before you approve each write. It guards on source-match and skips rows that already match.

          
    
            
  1. Search — filters All tasks to the key (hard reload) and auto-opens it when exactly one task matches; if several match, it reports the count and you open the right one with 👁.
    2. 
            
  2. Check — reads the live segment; flags source mismatch / already-correct.
    3. 
            
  3. Write + confirm — types the Final Translation and ticks proofread ✓✓.
    4. 
          

          
Stops at confirmed — you resubmit the task in Starling. Only TikTok source/target text is used; no Feishu doc or shared credential is sent anywhere.

        ℹ️ How Crowdin works
        

          
Harvest lists the file's source strings via the official API (GET /projects/<id>/strings) plus their current Hebrew. GPT-5.4 proposes a translation per string. Enter posts it (POST /projects/<id>/translations, unapproved) so it appears in the editor for you.

          
The tool never approves/submits — you do the final approve in the Crowdin editor. Only the source text is sent to OpenAI; your Crowdin token only talks to api.crowdin.com.

        ℹ️ How memoQ works
        

          
Harvest reads every segment through memoQ's editor API (POST …/docs/<id>/rows) — source, current Hebrew, inline tags, and confirmed status — in your logged-in session. GPT-5.4 proposes a translation per segment. Write saves it to the segment's target (PUT …/rows/<id>) as an unconfirmed draft.

          
The tool never confirms/delivers — you confirm each segment in memoQ. Inline tags are round-tripped exactly; if GPT drops a tag, that segment is refused (write it by hand) rather than saved wrong. Only source/target text is sent to OpenAI.

        ℹ️ How YiCAT works
        

          
Harvest reads every segment through YiCAT's segment API (GET …/cat/segment?…&seg_range=1-N) — source, current Hebrew, real inline placeholder tags, and confirmed status — in your logged-in session. The cosmetic whole-segment <g1> style wrapper is stripped and not treated as a tag. GPT-5.4 proposes a translation per segment.

          
The default is copy — you paste each proposal into the target cell and confirm it yourself. The auto-write drives YiCAT's own in-cell editor (Tiptap) and reads the cell back to verify — it reports failure rather than claiming a write it can't confirm. By default it writes a tracked change (old struck out, new marked inserted, exactly like manual editing); if that can't be verified it safely falls back to a plain untracked write. It skips segments with real tags and never confirms/delivers. Only source/target text is sent to OpenAI.
